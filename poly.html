One toolchain for three languages.

Poly is a build system and package manager for Rust, C/C++ and Go, in development. A project gets one manifest, poly.ini, and one lock file, poly.lock, no matter how many of the three languages it uses.

It isn't a wrapper. Poly drives rustc, gcc, clang, msvc and go tool directly, and it's meant to replace Cargo, CMake, Make and go mod rather than call them.

Poly will replace Jiggle, which is going to be deprecated.

Nothing is released yet. This page describes the 0.2 draft spec.

Read the spec!

What it's built around.

I

Native, not a wrapper

Poly calls the compilers itself. It resolves dependencies, builds the graph, compiles incrementally and links.

II

Minimal config

One INI file that's easy to read, edit and parse.

III

Signed packages

Every package is a signed vfsx archive, checked before it's extracted.

IV

Unix-y

Familiar commands that are fast and compose well.

Config is plain INI.

[project]
name = my-app
version = 1.0.0

[target.lib]
language = rust
type = lib
sources = src/lib.rs

[target.crypto]
language = c
type = static-lib
sources = src/crypto/*.c, src/crypto/*.h
compiler = clang
flags = -O3, -Wall

[target.server]
language = go
type = bin
sources = cmd/server/*.go
cgo = true

[dependencies.rust]
serde = 1.0
tokio = 1.0|full

[dependencies.c]
openssl = 3.0|poly
libz = 1.2|system

[dependencies.go]
github.com/gorilla/mux = 1.8
Sections
Dots make a hierarchy, so [target.lib] is the target "lib" and [build.profiles.release] is nested.
Arrays
Comma-separated: flags = -O3, -Wall.
Metadata
A pipe adds details to a value. tokio = 1.0|full turns on the "full" features, and openssl = 3.0|poly pulls from the Poly registry.
Sources
Dependencies can come from poly (the signed registry), system (through pkg-config), git or path.

One lock file for everything.

Dependencies for all three languages are resolved together and recorded in a single poly.lock, with a checksum and a signature for each one.

poly add rust:serde
poly add c:openssl
poly remove go:github.com/lib/pq
poly update                # everything
poly update rust:tokio     # one dependency
poly outdated
poly tree
poly lock

Compiler drivers, not wrappers.

Rust
Calls rustc directly. Poly works out the crate graph by reading the sources, handles features and cfg itself, and tracks dependencies for incremental builds.
C / C++
Detects gcc, clang or msvc. Source lists and globs come from poly.ini, headers are scanned so changes trigger rebuilds, and pkg-config is used for system dependencies only.
Go
Calls go tool compile and go tool link. Modules are read from poly.ini and no go.mod is used. It handles vendoring and CGO.

Cross-compiles by default. Every poly build produces binaries for both Windows and Linux—there's no flag to pick just one OS. Artifacts go to dist/{profile}/, organized by platform, and each platform's binaries are packaged as a VFSX archive.

poly build                          # all targets, Windows + Linux
poly build --release                # release profile
poly clean

Output: dist/debug/linux/, dist/debug/windows/, and dist/debug/{project}-{platform}.debug.vfsx archives.

Signed by default.

A Poly package is one vfsx archive, like my-app-1.0.0.vfsx.tar.zst. It holds the source, the lock file, a signed manifest, and one executable per platform. Each executable contains every language the package uses, so there are no per-language binaries to install.

Downloads are verified before they're extracted, and published packages are signed automatically.

[vfsx]
sign = true
keyfile = ~/.poly/private.pem
verify = true
trustStore = ~/.poly/trust/
poly sign
poly verify
poly trust add axiomwtf
poly trust list
poly trust remove <key>
poly publish

Roadmap.

1. Core
The poly.ini parser, poly.lock generation, a SAT-based dependency resolver, basic rustc, gcc and go drivers, a simple task graph and a basic cache.
2. Languages
Full Rust, C/C++ and Go drivers, plus unified linker orchestration.
3. Integrations
vfsx signing and verification, and the package registry client.
4. Developer experience
Test runner, linting and formatting, docs, shell completion and IDE integration.
5. Advanced
Toolchain management, cross-compilation, CI generation, migration tools and plugins.
6. Registry
The crates.io registry, package analytics, private registries and binary distribution.
Later
Possibly more languages, such as Zig, Nim, Java/Kotlin and JavaScript/TypeScript.
